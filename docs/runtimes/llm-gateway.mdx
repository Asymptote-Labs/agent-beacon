## Overview

Teams that route their agents' model traffic through an LLM gateway can record it there, without
installing anything on developer machines. `beacon-gateway` (the `gateway/` module in this
repository) attaches to the gateway's hook, decodes each model call, and writes Beacon events in
the [runtime JSONL schema](/telemetry-schema/event-schema), marked
`harness.collection_method: gateway`.

A gateway sees the conversation as the model receives it: the system prompt, the tool catalog,
the user's turns and the tool results on the way in, and the model's text, token counts and tool
calls on the way out. It does not see the agent's own lifecycle (approvals, hooks, files the agent
wrote without a tool call), so gateway events complement endpoint collection rather than replace
it. `endpoint` on a gateway event is the gateway host, and `user` is the identity the gateway
resolved for the call.

## Supported gateways

| Gateway | Hook |
|---------|------|
| LiteLLM proxy | `generic_guardrail_api` guardrail, `pre_call` and `post_call` |
| Envoy, Envoy Gateway, Istio | External Processing (`ext_proc`) filter |
| Portkey AI Gateway | `default.webhook` guardrail |

Model protocols: Anthropic Messages, OpenAI Chat Completions and OpenAI Responses, as JSON or
server-sent events.

## Run it

```bash title="Build and run"
cd gateway
go build -o beacon-gateway ./cmd/beacon-gateway
./beacon-gateway -config deploy/beacon-gateway.yaml
```

`gateway/deploy/` holds a commented configuration and example LiteLLM and Envoy configurations.
They observe only: LiteLLM lets calls through when the gateway is unreachable, and Envoy streams
replies to the client as they arrive. Events go to the JSONL files the `outputs` section names;
`beacon scan --log-path <file>` runs threat rules over them like any runtime log.

To record identifiers, paths, commands, models and token usage but no prompt, reply, instructions,
tool arguments or tool results, set:

```yaml title="Metadata only"
content:
  retention: metadata
```

## What gets recorded

| The call carries | Event |
|------------------|-------|
| System text, the first time a session sends it | `session.context` |
| An MCP tool definition, the first time | `mcp.tool_listed` |
| New user text | `prompt.submitted` |
| The model's text | `agent.message` |
| The reply's token counts | `token.usage` (`gen_ai.usage`) |
| A shell, read or MCP tool call | `command.executed`, `file.read`, `mcp.tool_invoked` |
| A fetch or any other tool call | `tool.invoked` |
| A read's or MCP tool's result | `file.read`, `mcp.tool_invoked`, with the result and the call's arguments but not its path or MCP server, which the call carries |
| Any other tool result | `tool.completed`, or `tool.failed` for an error |

Tool calls are recorded when the model makes them, before the agent acts on them. Replies carry
`gen_ai.response.id`, the provider's message id, which is the same id the endpoint's session
readers record, so a gateway's and an endpoint's record of one model call can be matched.
