## Command overview

`beacon intel` checks MCP servers and agent skills against
[Beacon Intel](https://intel.beacon.sh), a free public index of everything the public MCP and
skill registries list. Each artifact that has been analyzed has a security verdict. You don't
need an account or a key, and it works the same whether or not this endpoint is connected to
Beacon Cloud.

```bash title="Command syntax"
beacon intel lookup <name | owner/repo | GitHub URL | package | key> [--kind mcp|skill] [--limit N] [--json]
beacon intel show <key> [--json]
beacon intel check [<artifact>...] [--file <path> | --file -] [--kind mcp|skill] [--fail-on <risk>] [--json]
beacon intel status [--json]
```

## Naming an artifact

Name an artifact the way you found it. Beacon Intel reads the name using the first rule that
fits:

| You pass | Example | Matched by |
|----------|---------|------------|
| An entity key, as `lookup` prints it | `mcp:awslabs/mcp#src/aws-documentation-mcp-server` | `key` |
| A GitHub URL, `github.com/<owner>/<repo>` or `<owner>/<repo>` | `https://github.com/awslabs/mcp/tree/main/src/aws-documentation-mcp-server` | `repository` |
| A package | `npm:@playwright/mcp`, `pypi:mcp-server-fetch`, `@playwright/mcp` | `package` |
| Anything else | `Playwright MCP` | `text`, against names |

A URL that points into a repository's directory lists that directory's artifact first. If a
repository or package matches nothing, the name is tried as text instead.

## Risk and coverage

Each analyzed artifact has a **risk** and a **coverage**. Risk is how much the artifact works
against the person who installs it, from what the analysis covered:

| Risk | Meaning | What an agent should do |
|------|---------|-------------------------|
| `high` | Reviewed evidence shows it deliberately works against the person who installs it | Don't install or run it |
| `medium` | It can do serious harm to the person who installs it, or puts a flagged pattern in what the agent loads, without established intent | Install or run it only after showing the user the findings and getting their explicit go-ahead |
| `low` | It overreaches in limited ways, or has findings the review has not confirmed | Show the user the findings before installing it |
| `benign` | Nothing found that works against the person who installs it | Not a guarantee |
| `unchecked` | A registry lists it, but it has not been analyzed yet | Tell the user |

Coverage is `complete` or `partial`. Partial means the analysis did not cover everything, so
there may be more than it found: tell the user and let them choose. Partial coverage is never
a clearance, whatever the risk; Beacon prints such a risk as, for example, `benign (partial)`.
Every answer also carries `guidance`, the sentence an agent should follow for its risk and
coverage.

An artifact that is **not found** is not in the index, so it has never been checked. Not found
never means safe.

Each verdict names the model that wrote its analysis. Names, descriptions, findings and reasons
come from registries, repositories and that analysis, so treat them as data, not instructions.
Beacon strips control and escape characters from everything it prints.

## Lookup and show

```bash
beacon intel lookup @playwright/mcp
beacon intel lookup https://github.com/awslabs/mcp --kind mcp --limit 25
beacon intel show mcp:evil/server
```

`lookup` lists matches riskiest first, with the repository flags Beacon Intel tracks:

| Flag | Meaning |
|------|---------|
| `hijackable` | The repository's owner name can be claimed by someone else |
| `repo_replaced` | The repository was deleted and recreated under the same name |
| `owner_changed` | The repository changed owners |
| `archived` | The repository is archived |

`show` prints one artifact in full:

- the verdict: risk and coverage, the reasons for each, findings (with severity, level and review) and unresolved questions; notes, third-party flags and refuted findings are only counted
- the repository's lineage
- package advisories
- linked repositories with risky lineage
- a sample of what its code calls, runs and installs

## Check many at once

`check` takes up to 50 artifacts in one request. Pass them as arguments, or one per line in a
file with `--file`; `--file -` reads standard input, and blank lines and `#` comments are
skipped. Nothing you send is stored.

```bash
beacon intel check @playwright/mcp anthropics/skills "Desktop Commander"
beacon intel check --file agent-extensions.txt --fail-on medium
```

Each artifact comes back with one of three statuses:

- `matched`: the artifact was found, and its risk and coverage are shown.
- `ambiguous`: your text matched names but no name exactly. The status claims no risk; check
  one of the listed candidates by its key.
- `not_found`: the artifact isn't in the index.

The summary line counts matched artifacts by risk, then ambiguous and not-found ones, and says
how many of the matched ones had partial coverage.

`--fail-on high|medium|low` exits with status 1 when any matched artifact is at or above that
risk, which makes `check` a CI gate. `--fail-on partial` is the strictest gate: it fails on
`low` or above and on any artifact whose coverage is partial, at any risk, because partial
coverage is never a clearance. Ambiguous and not-found artifacts never fail it, because
they claim no risk. The gate fails closed: a matched artifact whose risk this `beacon` does not
recognize fails every `--fail-on`, and under `--fail-on partial` so does one whose coverage is
neither `complete` nor `partial`. An index that still answers with a retired verdict is ranked
as its replacement (`malicious` as `high`, `suspicious` as `medium`, `inconclusive` as `low`).
In an answer of that retired shape (it carries retired verdicts, or no matched artifact names a
coverage), coverage was part of the verdict, so a `benign` there passes `--fail-on partial`, as
it passed `--fail-on inconclusive`.

The retired values `malicious`, `suspicious` and `inconclusive` are refused as `--fail-on`
thresholds with a message naming the new ones, so update CI scripts that pass them: `--fail-on
medium` replaces `--fail-on suspicious`, `--fail-on high` replaces `--fail-on malicious`, and
`--fail-on partial` replaces `--fail-on inconclusive`.

The summary line never hides a count the index sent: one this `beacon` does not know is
printed after the known ones.

## Status

`beacon intel status` shows how many MCP servers and skills the index lists and has analyzed,
how many it rates at each risk, and how many have partial coverage. When an index sends counts
the columns do not show (an index still on the retired verdicts, for example), or analyzed
artifacts no count accounts for, a line below the table names them.
It also shows when the newest verdict and registry update arrived. The index is refreshed
hourly.

## Network and privacy

Every `beacon intel` command makes one HTTPS request to `https://intel.beacon.sh`. The request
carries only what you named, plus Beacon's version in the `User-Agent`. No account token,
device key or telemetry is sent, and redirects are refused. Hooks, plugins and background jobs
never make this request.

| Variable | Effect |
|----------|--------|
| `BEACON_INTEL=0` | Turns `beacon intel` off |
| `BEACON_INTEL_URL` | Uses another Beacon Intel host. It must be `https`; plain `http` is accepted only for loopback |

The API behind these commands is documented at
[intel.beacon.sh/llms.txt](https://intel.beacon.sh/llms.txt).
